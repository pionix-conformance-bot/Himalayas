164 /// \brief Dispatch a \c PullDynamicScheduleUpdateRequest for \p charging_profile_id.
165 ///
166 /// Single-flight: if a pull for this id is already in flight (present in \ref pending_pulls),
167 /// the dispatch is skipped without emitting a wire request and \c true is returned, so the
168 /// timer advances the deadline normally. Otherwise the response future is stored in
169 /// \ref pending_pulls and consumed by the single \ref reaper_loop thread (not the timer's
170 /// io_context) so a slow CSMS cannot block the timer or deadlock by re-entering
171 /// \ref update_tracking on the timer thread.
172 ///
173 /// \return \c true on successful dispatch (or single-flight skip); \c false when
174 /// \c dispatch_call_async throws synchronously (queue full, websocket down, serialization
175 /// failure). On \c false, the timer-thread caller must skip the deadline overwrite so the next
176 /// tick retries promptly.
177 bool dispatch_pull_request(std::int32_t charging_profile_id);
178
179 /// \brief Single reaper thread: poll every in-flight pull future in slices, applying each
180 /// response as it lands. One thread services all \ref pending_pulls regardless of count; the
181 /// per-pull deadline bounds each wait, and \ref teardown_requested is observed every slice so
182 /// the destructor join cannot hang on a silent CSMS. Validates each response (timeout,
183 /// future-throw, offline, unexpected type) before calling \ref apply_pull_response.
184 void reaper_loop();

186 /// \brief Parse the response, re-look-up the profile
187 /// (it may have been cleared/replaced in flight), and apply the schedule update.
188 /// On success the recompute callback is fired first and the pull deadline is
189 /// advanced only afterwards, so a callback failure leaves the deadline unchanged
190 /// and the next tick retries. Logs and returns on any non-actionable state (parse
191 /// fail, not Accepted, profile gone/non-Dynamic, persist fail).
192 void apply_pull_response(std::int32_t charging_profile_id,
193 const ocpp::EnhancedMessage<MessageType>& enhanced_message);

206 /// \brief Set by the destructor before joining the reaper. The reaper observes this each poll

209 /// \ref pending_pulls and \ref reaper_thread so destruction tears down in the reverse order.

212 /// \brief In-flight PullDynamicScheduleUpdate responses, multiplexed onto \ref reaper_thread.
213 /// A vector (not a thread_safe_queue) because the reaper must scan all entries each tick and
214 /// erase arbitrary entries on completion/timeout, and \ref dispatch_pull_request scans it for
215 /// the single-flight check. The monitor's own condition variable wakes the reaper on a fresh
216 /// dispatch or on teardown. Pushed by the timer thread (the sole producer); entries are only
217 /// removed by the reaper, so the single-flight check-then-push is race-free.
218 everest::lib::util::monitor<std::vector<PendingPull>> pending_pulls;
